# 低代码开源音乐结构化方案

**作者：Manus AI**  
**日期：2026-08-22**

## 结论：不要找“一个万能仓库”，而要建立一个很小的三件套

你的目标不是做新的音乐理解研究，也不是训练一个“听懂音乐”的大模型；你要的是把自己做好的音乐放进去，稳定得到一份**人和后续智能体都能读的结构化档案**。因此，最合适的第一版不是 MOSS-Music-Data-Pipeline，也不是 MOSS-Music 这类大模型，而是：

> **`allin1` 负责曲式与拍点；`Essentia` 负责可复核的数值、节奏与调性特征；你自己的 `JAMS + Music IR JSON` 负责保存与统一这些结果。**

这是一个“小而正确”的底座。它只依赖两个主要分析器，输出原生就是 JSON，基本不需要自己实现音乐算法，也没有 GPU、Ray 集群、外部大模型服务或大规模训练语料的前置要求。`allin1` 已可直接预测 BPM、beat、downbeat 与 intro/verse/chorus/bridge/outro 等功能段落，并以 JSON 输出；`Essentia` 的命令行音乐提取器可输出 JSON/YAML，覆盖声学、节奏、调性与可选高层描述符。[1] [2]

| 层次 | 你应该用什么 | 它回答的问题 | V0.1 是否必选 |
|---|---|---|---:|
| 曲式 / 时间骨架 | **allin1** | 这首歌多快？每拍在哪？哪里像 intro、verse、chorus？ | 是 |
| 音乐与声学证据 | **Essentia Music Extractor** | 调性候选、BPM、动态、响度、频谱重心、onset 密度等是什么？ | 是 |
| 保存与规范 | **JAMS + `music-ir.json`** | 如何保存原始、带时间的证据，并提供简洁的可读摘要？ | 是 |
| 音符 / 旋律骨架 | **Basic Pitch** | 能否生成 MIDI 与音符事件的候选版本？ | 按需 |
| 语言化描述与问答 | **MOSS-Music** | 这段听起来像什么？乐器、情绪、制作感如何？ | 后期可选 |
| 大规模数据生产 | **MOSS-Music-Data-Pipeline** | 如何为大量歌曲并行产出训练语料？ | 不用 |
| 可视化上传与自动化 | **n8n** | 如何做文件夹监控、上传、批量调度？ | 流程稳定后再加 |

## 你真正要构建的东西：Music IR，而不是“音频转文本”

> **Music IR（Music Intermediate Representation）** 是一份分层 JSON：它保留“这个结论来自哪个工具、发生在什么时间、可信度如何”，又把真正要被使用的内容整理为全曲、段落、和声、事件与声学特征。

不要直接把音频、频谱图、长串 embedding 或一个巨大的 MIDI 文件塞给后续智能体。这样一来，智能体会失去时间结构、证据来源和“不确定性”的边界。更合理的模式是：音频经过多个专用工具后，形成可验证的事实层；需要解释或做 SuperCollider 映射时，再让智能体读取凝练的 `music-ir.json`，并在必要时回查原始数据。

```text
你的成品 .wav / .flac
          │
          ├── allin1 ────────> BPM / beats / downbeats / sections.json
          │
          ├── Essentia ──────> key / tonal / rhythm / loudness / spectral.json
          │
          └── Basic Pitch ───> midi + note-events.csv（仅按需）
                                      │
                                      ▼
                  原始证据：analysis.jams + raw/*.json
                                      │
                                      ▼
                    使用层：music-ir.json
                                      │
                 ┌────────────────────┴───────────────────┐
                 ▼                                        ▼
       后续音乐智能体 / 检索 / 比较                 SuperCollider 映射与人工复核
```

JAMS 已为 beat、chord、key、pitch、segment、tempo 等常见音乐注释定义了 schema，并能在同一文件中保存多套注释、验证错误和对接 `mir_eval`；这正适合当“证据封存层”。[3] 但 JAMS 不是为声音合成控制设计的，因此要在其旁边维护一个更简洁的 `music-ir.json`：前者保存所有原始观察，后者保存你的最终工作语言。

## 为什么不是 MOSS-Music-Data-Pipeline

已有研究里提到的 MOSS-Music-Data-Pipeline 在思路上很对：它并行结合音频语言模型描述、Chordino + BeatNet + Essentia 的 MIR 特征和 SongFormer 的结构分段，再合并为 JSONL。它非常适合作为**架构参考**。[4]

但它并不适合你现在直接当底座。官方快速开始需要下载约 8GB 权重；其本地流程用 Ray 承载 CPU/GPU 模块，SongFormer 要本地 GPU，同时还预期单独部署音频语言模型、歌词 ASR 与最后的 LLM 服务。[4] 这是“批量生产模型训练语料”的系统，不是“我有一首自己做好的音乐，希望点一下就得到结构化档案”的系统。

同样，MOSS-Music 的两种公开模型各约 9.1B 参数，尽管它能做歌词、描述、和声/速度/调性推理、结构与长曲问答，仍应在后期作为**语义说明器**，而不是第一版的事实引擎。[5] 已有基准研究显示，多模态模型在直接从音频完成核心音乐感知时并不如在 MIDI 等符号输入上稳定，因此节拍、调性、和声和曲式应由专门 MIR 工具交叉提供证据。[6]

## 推荐组合的职责与边界

| 工具 | 推荐理由 | 你会实际得到什么 | 绝对不要误解成什么 |
|---|---|---|---|
| **allin1**（MIT） | 单个命令或 Python 调用即可给出全曲 BPM、beat、downbeat、功能段落和 JSON；最贴近“少写代码”的结构层。[1] | `bpm`、beat/downbeat 时间点、`{start, end, label}` 段落 | 自动理解作曲意图，或逐小节可靠地识别和声 |
| **Essentia**（AGPL-3.0） | 有预构建命令行提取器；可用 YAML profile 固定分析条件、输出 JSON，适合得到可重复的音乐/声学证据。[2] | 响度、动态、谱质心、MFCC、BPM、拍点、onset、调性候选、和弦统计 | “dark”“warm”“cinematic”等主观语义的唯一真值 |
| **JAMS** | 成熟的带时间音乐注释规范，支持多注释、schema 验证和常用 MIR namespace。[3] | `analysis.jams`：原始事实、多个候选、工具与版本 | 面向合成控制或智能体推理的最终语言 |
| **Basic Pitch**（Apache-2.0） | CLI 轻量，可输出 MIDI、CSV note events 和 sonification；适合验证旋律/单一素材的音符轮廓。[7] | MIDI 和按时间排列的音符候选 | 成品混音的完整多轨乐谱；官方也明确它在单乐器场景最佳。[7] |

对于 Essentia，需要特别注意许可证。它是 AGPL-3.0；你若在自己的机器上或开源项目里使用，技术上仍然是一个非常强的选择；但若今后把它封入面向外部用户的闭源在线服务，应在发布前单独进行许可证合规审查。[8] 如果你目前主要是为自己的音乐工作流服务，不要因这个问题阻塞 V0.1；只要把它明确记录为架构约束即可。

## 你的基础仓库应该长什么样

你需要的是一个非常薄的“胶水仓库”，而不是 fork 一个庞大的研究项目。建议命名为 `audio-to-music-ir`。它自己的代码量应当很小：两个固定 profile、一个顺序运行入口、一个把原始 JSON 合并到目标结构的转换器，以及文档。真正复杂的分析全部交给已有开源仓库。

```text
audio-to-music-ir/
├── README.md                         # 安装、运行、字段解释与许可证说明
├── source/                           # 放入你自己的 .wav / .flac；不提交到 Git
├── profiles/
│   └── essentia_v0_1.yaml            # 固定的分析参数，保证跨曲可比
├── raw/                              # 各工具原始输出，保留为证据
│   ├── allin1/
│   ├── essentia/
│   └── basic-pitch/                  # 可选
├── jams/
│   └── track-id.analysis.jams        # 标准化的时序注释封存
├── music-ir/
│   └── track-id.music-ir.json        # 给人/智能体读取的凝练结构
├── schemas/
│   └── music-ir-v0.1.schema.json
├── run_analysis.sh                   # 顺序调用现成 CLI；不训练、不爬取、不起服务
├── build_ir.py                       # 很薄的 JSON 合并与字段映射；唯一必要的小段代码
└── docs/
    ├── field-guide.md                # 每个字段能、不能说明什么
    └── review-checklist.md           # 人工复核段落、调性、节拍的步骤
```

这里唯一“自己写”的部分是 `build_ir.py`，但它不做任何音乐识别；它只是把 `allin1.json` 和 `essentia.json` 放到你定义的位置，写入工具版本、profile 名称、源文件 hash 和人工复核状态。这样即使未来替换某个模型，也不需要改变你的全部项目。

## V0.1 应该保存哪些数据

第一版不要贪心，更不要强行把“制作感”自动翻译成合成器参数。先保存你确实需要且能复核的东西。已附上 [`music_ir_v0_1.example.json`](./music_ir_v0_1.example.json) 作为可直接改名使用的样例。

| 区域 | V0.1 字段 | 来源 | 用途 |
|---|---|---|---|
| 全曲 | 时长、BPM、调性候选与强度 | 音频元数据、allin1、Essentia | 设定时间网格与整体音乐语境 |
| 曲式 | beat/downbeat、段落起止、段落标签 | allin1 | 把作品拆成可讨论的部分 |
| 和声 | 调性候选、和弦统计、变化速率 | Essentia | 提供和声概览，不伪装成逐时和弦真值 |
| 声学 | LUFS、动态范围、谱质心、flux、onset rate、MFCC | Essentia | 比较段落、比较重建版本、描述能量和频率质感 |
| 符号（可选） | MIDI、note-events CSV | Basic Pitch | 给旋律/节奏骨架一个可编辑候选 |
| 溯源 | 工具、版本、profile、原始文件路径、人工复核状态 | 你的胶水层 | 使结果可复现、可质疑、可更新 |

音符转录只在两种情况下开启：其一，你的素材本来就是独奏或清晰主旋律；其二，你真的需要让后续系统以 `Pbind` 一类音符事件为起点工作。对于已经混好、层次很多的成品，Basic Pitch 的结果要被标记为 **candidate**，而不是 `truth`。

## 实施顺序：先用、再自动化、最后才加大模型

第一周只做两首作品的本地实验。将 WAV 或 FLAC 放进 `source/`，分别运行 allin1 与 Essentia，观察每首作品是否得到合理的 BPM、拍点、曲式分段、调性候选和动态/频谱档案。用耳朵核对每个段落边界与调性；把发现的问题记录进 `review` 字段。此阶段的成功标准是：你可以打开一份 JSON，就知道“曲子从哪里开始、哪里变化、总体节奏/调性/能量如何”，而不是追求自动生成漂亮文字。

第二步才加入 `analysis.jams` 与 `music-ir.json`。原始工具输出完整保存，转换器只提取稳定字段，并写入 provenance。这样你以后要换结构模型、更新 Essentia 或加逐时和弦模型时，历史结果仍然可以回溯。

第三步再决定是否加入 Basic Pitch。选一首旋律线清晰、配器较简单的曲子验证 MIDI 是否有用。若它只制造大量错误事件，就关闭这个通道；这不是失败，而是在保护 Music IR 的可信度。

最后，如果你已经积累了足够的结构化档案，并希望能用自然语言询问“哪一段最稀疏、哪一段有高频上升、这首与另一首在哪些方面相似”，再加 MOSS-Music 或其他音频语言模型。到那时，它读取的是已有事实和音频，而不是被迫单独判断一切。

## 不建议现在做的事情

第一，不建议现在 fork MOSS-Music-Data-Pipeline 当主项目。它会迫使你先处理 GPU、模型服务、Ray、ASR 和多阶段失败恢复，而你真正需要的只是少数稳定的 JSON。第二，不建议强制做 source separation；只有在某首混音确实让你无法获得主旋律或鼓击证据时，才将其作为辅助观测。第三，不建议一开始上 n8n：它虽然能将本地文件与命令做成可视化流程，但自托管下的 Execute Command 有明确安全风险且默认禁用，容器还会引入文件挂载和权限问题。[9]

> **最短答案：先用 `allin1 + Essentia + JAMS/Music IR`。需要音符时再加 Basic Pitch；MOSS 系列和 n8n 都放到第二阶段。**
